ep14で「NODE-07は受信側」という根本的な転換が起きた。ep15はその転換を受けて「では送信側をどう探すか」の調査を具体的に動かす章。技術的な発見（QY-系列識別子の可能性）と人的接触（シリア・イレーネ）の両輪を動かし、次の調査方針を二つ用意して章を閉じる。

## シーン構成

### Scene 1 — 朝：receive_logの照合（全体の約30%）

**場所**: テルの部屋 / 黒板
**目的**: 「送信側を探す」という昨夜の問いを、朝の黒板作業として動かす

**流れ**:
1. 黒板を開いたテルが、昨夜の最後の問いを確認する内部描写
2. 「受信記録を逆算できないか」という仮説を立て、receive_logを照合しようとする
3. 返ってくる：受信コンテンツは揮発性・保存なし（想定内）
4. ではコンテンツではなく「形式の痕跡」を問えないか → receive_format_traceを試みる
5. ここで何かが返ってくる

**黒板コードブロック**（二段構成）:

```
> describe --target=NODE-07 --field=receive_log
[receive_log: 揮発性]
[コンテンツ保存: なし / 受信完了後に廃棄]
```

→ テルの内部：予測通り。でも、コンテンツではなく形式が残っていれば。

```
> describe --target=NODE-07 --field=receive_format_trace
[receive_format_trace: 参照可]
[形式マーカー: 検出済み]
[マーカープレフィックス: QY-]
```

**発見のポイント**:
- 「参照可」が返ってきた。これまでの「参照不可」「UNDEFINED」と違う種類の返りだ。
- マーカープレフィックス：QY-。
- （……QY-。NODE-07のQY-と、同じ頭だ）
- テルが気づく：「QY-NODE-07」の「QY-」は、ノードの名称の一部だと思っていた。でも、これは形式のマーカーにも「QY-」が使われている。「QY-」はノード名称ではなく、形式の系列識別子かもしれない。

**Show, don't tell の注意点**:
- テルが「これは大きな発見だ」と語るのではなく、指が止まる・チョークを持ち直す・もう一度読み返す、などの動作で示す
- 発見の重さは短文の積み重ねで表現する

## 用語解説（今章の新出IT用語）

以下の用語を章末解説に含める:

1. **receive_log（受信ログ）**: システムが受け取ったデータの記録。ただし、揮発性の受信では受信完了後にコンテンツが廃棄され、「何を受け取ったか」は残らないことがある。

2. **receive_format_trace（受信形式の痕跡）**: コンテンツ自体は消えても、「どういう形式で受け取ったか」という形式の記録が別途残ることがある。この話では、コンテンツは揮発性で廃棄されていたが、形式マーカー（QY-プレフィックス）の痕跡は消えずに残っていた。

3. **プレフィックス（prefix）**: 名前や識別子の先頭につく決まった文字列。「QY-NODE-07」の「QY-」の部分がこれにあたる。ノード名の一部だと思われていたが、形式の系列を示す識別子として機能している可能性がある。

4. **format_series（形式系列）**: 同じ設計思想・仕様から生まれた複数の形式をまとめたグループ。「QY-系」という系列が存在するとすれば、NODE-01からNODE-07まで、同じ形式の系譜に属している可能性がある。
